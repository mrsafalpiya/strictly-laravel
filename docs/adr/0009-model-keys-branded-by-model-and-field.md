# Model keys are branded by their model and field, declared with #[KeyOf]

A key a Data property holds is generated as `Key<'Issue', 'id', number>`: a number (or string) branded with the model's class basename and the field it is a key of, so another model's key, another field of the same model (an issue's per-project `number` where its `id` is expected) and a plain number don't fit (P-128). The one brand serves every place a key goes: route parameters take the key of the field their route binds by, a Data class built from a model brands its primary key and the fields its routes bind by, and any property, in input and query classes too, declares a foreign key with `#[KeyOf(User::class)]` (the primary key unless it names a field). `#[RouteKeyOf]` and `RouteKey<'Issue', number>` stay as the special case of the route key name, which `strictly:generate` writes per model. Chosen over a second brand for non-route keys beside the model-only route-key brand (two brands for the same value, and the route-key brand let `issue.number` stand in for `issue.id`), over a PHPDoc type (`list<KeyOf<Issue>>`, which PHPStan and laravel-data would both have to learn) and over inferring the model from the `exists` rule or the property name (guesses that break on `Rule::exists()` with a custom query or an `assigneeId` holding a `User` key). Enforced by a PHPStan rule on names and `exists` rules rather than left optional, at the cost of a breaking release: every existing key field must be annotated, and a select's value must be looked up among the keys the server sent instead of converted with `Number()`.
