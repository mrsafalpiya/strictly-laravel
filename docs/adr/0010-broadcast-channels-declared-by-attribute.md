# A broadcast event declares its channels with `#[BroadcastsOn]`, verified against `broadcastOn()` both ways

Every broadcast event names each channel pattern it is sent on with a repeatable `#[BroadcastsOn('issues.{issue}')]`, required by the PHPStan rule `strictly.broadcastsOn`, and `strictly:generate` maps each pattern to the events declared on it (`ChannelEvents`), so `useChannelEvent()` takes an event only on a channel handle whose pattern declares it (Problem P-144). The generator can't read the channels from `broadcastOn()`, which builds their names at runtime (`"issues.{$this->issue->id}"`), so the declaration duplicates it; we accept that and verify it in both directions instead: a recorded broadcast on a channel whose pattern the event doesn't declare fails its Contract, and a declared pattern no feature test broadcasts the event on is a Contract Coverage gap. The alternatives were a typed channel builder used inside `broadcastOn()` whose pattern is a literal, which the generator would have had to find by static analysis of every event's method body and which changes how every event builds its channels, and an optional declaration with undeclared events allowed on any channel, which leaves P-144 open for every event that forgets it. A pattern must name a channel the app knows (`routes/channels.php`, or `public_channels` in `config/strictly.php`), or generation fails.
