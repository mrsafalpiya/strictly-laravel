# The fixture-app harness

The harness is the primary test seam for the Overlay. It generates the latest Base Kit, installs both Overlay packages from this repo's local paths, runs `php artisan strictly:install`, optionally applies a **scenario** (a set of file edits), runs the app's `composer ci:check` (or one step of it), and asserts the outcome: pass, or fail with an expected error substring. Test the Overlay here, the way an app developer meets it. Don't assert on generator internals.

## Commands

Run these from the repo root. First-time setup: `composer install && pnpm install`.

| Command | What it does |
|---|---|
| `pnpm test` | Full suite: version sync, fresh install passes `ci:check`, `strictly:install` is idempotent (a re-run changes nothing and reports every row `unchanged`), a re-run restores a missing hook and reports one it can't apply without touching that file, the dev server and build warn when the Composer and npm package versions differ, Kit Conversion leaves unknown content alone, feature tests record Contracts even when Kit Conversion skipped an edited `tests/Pest.php`, its manifest records every earlier converted version, the oxlint plugin's rule-tester cases (`harness/tests/oxlint-plugin.test.ts`), the npm package's React helpers rendered by its own tests (`packages/npm/tests/`, next to the package so `react` resolves to its copy), generated TypeScript is gitignored and regenerated by `ci:check`, typecheck and build in a fresh clone, a running dev server regenerates types when a Data class is saved or a page file is created or deleted, and keeps them when a Data class is half-written, the Vite plugin's debounce and run queue through a real Vite dev server (`harness/tests/vite-plugin.test.ts`), every scenario. |
| `pnpm test <pattern>...` | Only the tests whose names match, e.g. `pnpm test example-type-error-fails-tsc`. |
| `pnpm harness` | Fresh install only: `strictly:install` and every `ci:check` step must pass on the latest Base Kit + Overlay (the nightly check). Each step runs on its own, and a failure names the stage and the files that broke. |
| `pnpm harness <scenario>... [--step <step>]` | Run the named scenarios and report each one. `--step` overrides the scenario's step. |
| `pnpm harness --list` | List the scenarios. |
| `pnpm harness --fresh` / `STRICTLY_FRESH_BASE_KIT=1 pnpm test` | Regenerate the latest Base Kit first. |
| `pnpm typecheck` | Typecheck the harness and the oxlint plugin (strict `tsc`, JSDoc types for the plugin's JS). |
| `pnpm lint:php` | Run Pint on the Composer package (`--test` to check only, as CI does). |
| `pnpm test:php` | The Composer package's PHPUnit tests: its PHPStan rules, through PHPStan's rule-test kit (`packages/laravel/tests/`). |

Timings on a warm cache: about 8 s for a scenario that runs a single step and about 20 s for a full `ci:check`. The full `pnpm test` takes about 2 min on 20 CPUs (8 apps at once) and about 5 min with 2 at once, using about 15 MB of disk and 0.6 GB of memory per app checked at once. A fresh Base Kit takes about 1.5 min to generate, plus about 20 s to install the packages.

## CI

| Workflow | When | Runs |
|---|---|---|
| `.github/workflows/ci.yml` | Every push to `main` and every pull request | `pnpm typecheck`, `pnpm lint:php --test`, `pnpm test:php`, then `pnpm test`. The runner starts with no fixture cache, so `pnpm test` always uses a freshly generated Base Kit. |
| `.github/workflows/nightly.yml` | Daily at 03:17 UTC, or by hand (`gh workflow run nightly.yml`) | `pnpm harness --fresh`: the fresh-install check against the latest upstream Base Kit. |

Both workflows share their setup through `.github/actions/setup` and upload `.fixtures/*.log` when they fail. Under GitHub Actions, `pnpm harness` also prints every fresh-install failure as an `::error` annotation titled `Fresh install failed at <stage>`. The stage is `strictly:install` or `ci:check:<step>`, and the annotation lists the files the tool named, so a red nightly run shows what broke on its summary page.

The files come from `harness/src/failure-report.ts`, which knows the output formats of tsc, oxlint, oxfmt, Pint, PHPStan, Pest and `strictly:coverage`. When no format matches, the report falls back to the tail of the output. When you add a `ci:check` step that runs a new tool, teach that module its format and add a unit test in `harness/tests/failure-report.test.ts` that uses the tool's real output. For `strictly:install` and `ci:check:install` (`strictly:install --check`), any installer row (`<label> .... <status>`) whose status isn't `applied` or `unchanged` counts as a failure; the check reads `missing` for a hook and `not converted` for a Base Kit file the installer would still change. A label without spaces is an app-relative path and is reported as the file: Kit Conversion reports each file as a row of its own, labelled with its path, a file it skipped reads `skipped (unknown content)`, and a Base Kit file it expected but didn't find reads `not found`. Such a row fails the fresh install even when `strictly:install` exits 0, as ADR-0005 requires of the nightly run, and every app `pnpm test` creates fails the same way. When generating the Base Kit or requiring the packages fails, the report names the failed command.

## Where the fixtures live

`.fixtures/` is gitignored. It is also an empty git repository of its own: oxlint and oxfmt honour `.gitignore` files up to the enclosing repo root, and without that boundary the monorepo's `/.fixtures/` rule would hide every fixture file from `vp check`.

| Path | Contents | Rebuilt when |
|---|---|---|
| `base-kit/` (+ `base-kit.stamp.json`, `base-kit.log`) | The output of `vendor/bin/laravel new base-kit --react --pest --pnpm --no-boost --database=sqlite --git --no-interaction`, using the `laravel/installer` pinned in the root `composer.json`. | `--fresh`, or the stamp is missing |
| `installed/` | `base-kit` with `mrsafalpiya/strictly-laravel` (a Composer path repo, symlinked) and `@mrsafalpiya/strictly-laravel` (`link:`) required, committed in the app's own git repo. The files in its `vendor/` and `node_modules/` are read-only. | The Base Kit or either package manifest changes. Package code is symlinked, so code edits need no rebuild. |
| `<app>/` (+ `<app>.log`, `<app>.tmp/`) | A throwaway copy of `installed/` with `strictly:install` already run: `fresh-install`, `idempotent-install`, `scenario-<name>`. `<app>.tmp/` is its `TMPDIR`. | Every run. It stays on disk afterwards for inspection. |

An app copies its own files and hard-links `vendor/` and `node_modules/` to `installed/`'s, which are about 97% of its size. That way an app costs about 10 MB and a second to create, instead of about 1 GB and 9 s. Because the dependency files are shared, they are read-only: a tool that rewrites one in place fails with `EACCES` or `Permission denied` instead of changing it for every later app. If a tool legitimately rewrites such a file (pnpm rewrites its install state when `package.json` changes), add the file to `appOwnedDependencyFiles` in `harness/src/fixture.ts`, so every app gets its own copy. Hard links need GNU `cp -l` and `.fixtures/` on one filesystem.

The test suite checks apps concurrently, and `pnpm harness <scenario>...` runs its scenarios concurrently too. Each app has its own directory and its own `TMPDIR`, so caches such as PHPStan's aren't shared. By default the number of apps checked at once is half the CPUs, capped at one per 2 GiB of memory; set `STRICTLY_HARNESS_CONCURRENCY` to override it, for example to `1` to debug a run one app at a time.

Every app is its own git repo. Run `git diff` in an app to see what `strictly:install` and the scenario changed. All apps sit at the same depth, so the relative symlinks that Composer and pnpm create still work in copies. Each `<app>.log` holds every command the harness ran in that app and its full output.

Every fixture command runs without the AI-agent environment variables (`AI_AGENT`, `CLAUDECODE`, …, taken from `laravel/agent-detector`). Under an agent, `laravel/pao` changes Pest's CLI and output, and the installer's Pest conversion breaks. Fixtures must behave the same for humans and agents.

## `ci:check` and its steps

`strictly:install` makes `ci:check` a sequence of named Composer scripts, so each step can run on its own as `composer ci:check:<step>`:

| Step | Runs |
|---|---|
| `install` | `php artisan strictly:install --check`: applies every hook and Kit Conversion to a scratch copy of the app and fails, naming each one, when the installer would still change something or can't apply a hook (P-080, P-082; the release checks in `packages/laravel/UPGRADE.md`) |
| `generate` | `php artisan strictly:generate`: the gitignored TypeScript generated from PHP (`@/generated` and Wayfinder's routes) |
| `lint` | `<pm> run check` (Vite+: type-aware oxlint with the Strictly Laravel oxlint plugin, + oxfmt) |
| `test` | `@test` (Pint, PHPStan, Pest). Every feature test records the pages it renders (their own props, the shared props and what was flashed) the flash data of the redirects it makes, and the validation errors of its requests to form endpoints as Contracts in the gitignored `resources/js/__contracts__` |
| `coverage` | `php artisan strictly:coverage --strict`: Contract Coverage over the Contracts the `test` step recorded. Fails on a page no test renders, a form endpoint (an action taking an input class) no test submits to, and on a shape no Contract showed (a nullable field only ever `null`, an Optional prop never sent, a list or map only ever empty, a Data union variant or scalar-union member never seen), one ` ✗ <gap> (at <where>): <the test to add>.` line each (P-066) |
| `tsc` | `<pm> run types:check` (`tsc --noEmit`): the app, and the Contracts the `test` step recorded |

`<pm>` is the package manager detected from the app's lockfile. `coverage` and `tsc` run after `test` so that they read and check the Contracts; run alone, they see whatever Contracts the last test run left (none in a fresh clone, which `coverage` reports). A scenario whose diagnostic is a failing Contract or a Contract Coverage gap runs the full `ci:check` (omit `step`). So does every passing scenario that adds a page, and its feature tests must render that page with every shape its props permit, or Contract Coverage fails it. The installer also makes the app's `build`, `build:ssr` and `types:check` scripts run `strictly:generate` first, so the `tsc` step works on its own from a fresh clone. Type errors only fail `tsc`: type-aware oxlint doesn't report them.

## Scenario format

```
harness/scenarios/<name>/
├── scenario.json
└── files/            optional; mirrored onto the app root (files are written or overwritten)
```

```json
{
    "problem": "none",
    "description": "What the scenario proves.",
    "step": "tsc",
    "expect": { "outcome": "fail", "errorContains": "error TS2322: Type 'string' is not assignable to type 'number'." },
    "delete": ["resources/js/some-file.ts"]
}
```

- `problem` (required): the id of the Problem it guards (from `docs/problems.md`), or `"none"` for examples and for enforcement that guards no single Problem (the description says what it enforces, citing the ADR if there is one).
- `description` (required): one sentence.
- `step` (optional): a `ci:check` step. When it's omitted the full `ci:check` runs. Use a single step for speed whenever the Problem is caught by one tool.
- `expect` (required): `{"outcome": "pass"}` or `{"outcome": "fail", "errorContains": "<substring>"}`. Failing means a non-zero exit code and the substring in the combined output, with ANSI codes stripped. Pick a specific diagnostic (an error code and message), not just a file name.
- `delete` (optional): app-relative paths removed before `files/` is copied.
- `reinstall` (optional, default `false`): run `php artisan strictly:install` again after the edits, as an app does after updating the packages, then the check. If the installer exits non-zero, its output is the scenario's result and the check doesn't run. Use it to prove that a re-run restores a hook (P-080) or reports one it can't apply (P-082).

Unknown keys are rejected. The examples are `example-typed-code-passes` and `example-type-error-fails-tsc`.

## Adding scenarios for a Problem

1. Reproduce the Problem in a scratch app (`pnpm harness`, then edit `.fixtures/fresh-install`) until you know the exact edit and the diagnostic the fix should produce.
2. Add a breaking scenario: the Problem's reproduction written the way an app developer would, with `expect.outcome` set to `fail` and the specific diagnostic.
3. Add a passing scenario: the typed way that should work, with `expect.outcome` set to `pass`.
4. Set `"problem"` to the Problem's id and `"step"` to the tool that catches it (full `ci:check` if several do).
5. Run `pnpm test <name>` and watch the breaking scenario fail for the right reason before the fix lands (red), then pass.
6. Before finishing, run `pnpm test` to make sure the fresh install still passes. Run it with `STRICTLY_FRESH_BASE_KIT=1` when upstream may have moved.
